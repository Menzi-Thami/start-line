# Private workout prescription pilot — implementation contract

Status: implementation on draft PR #332; verification in progress. No release or real-owner activation approval. This public document contains no real runner identity, dates, goals, performance history, health information, private payload or credentials. Use synthetic fixtures only.

## Architecture
Reuse the existing deterministic TrainingPlanGenerator, WorkoutBuilder, PlanBuilder, SavedPlan and authenticated /me/plans pipeline. SavedPlan is runner-owned; MyPlans handlers scope lookups to CurrentRunner and return 404 for another owner's plan. Keep the one-active-plan invariant and history. Do not alter generic generated schedules, historical generator versions or anonymous share URLs. PlanBuilder.Build and BuildPlan are used by different downstream consumers; ensure a single canonical owner-aware resolution path for all saved-plan reads (including coach, weekly recap, calendar, workout details, progress, ICS, check-ins, matching, export, archive and replan). Do not simply overlay a different UI DTO.

Implement an opt-in versioned private prescription associated with SavedPlan (not GeneratePlanQuery, public link parameters or anonymous generator). Store the actual schedule only in the protected application data store. Support an authenticated owner preview and activation using a private payload supplied by the owner outside this public repository; never seed a real runner by name/email/ID, put payload into code, CI, logs or PRs, or use production credentials for testing. Bind ownership from authenticated identity, not payload; keep feature access server-gated and fail closed. Use strict schema validation, bounded payload size, local dates, unique session identities, correct distance totals, legal pace ranges, no past/completed changes, correct race and no post-race sessions. Preserve row-version and preview token concurrency guarantees, transactional archive/activation, idempotency and existing privacy/deletion/export behavior. Public sharing must not serialize private prescriptions or private inputs; hide that affordance for a private plan, enforce server side where applicable. Clear sensitive offline cache on sign-out/account switch.

## Training and strength
TrainingPlanGenerator currently caps strength days at 3; do not globally raise this. Private prescription needs four gym slots with upper/lower classification, with lower load tapered on recovery/race weeks and optional easy or rest days. Reuse strength session presentation when compatible; ensure run and strength sessions can coexist on one day without collision in completion, movement, check-ins, keys or calendar. Generic schedules and existing strength validation must remain unchanged. Support explicit workout steps, warmup/cooldown included in distance, pace ranges, RPE, recovery and race-week exceptions. Preserve completed sessions when future work is adjusted. Adaptation must use runner-authored check-ins and permitted data only; follow docs/claude-pr295-execution-contract.md, do not use Strava-derived content in lasting coaching or circumvent provider terms. No automatic upward revision from a single session. Avoid catch-up mileage, hard day stacking, and unsafe overrides. If a feature cannot safely support private schedules, fail closed and explain; do not silently regenerate generic workouts.

### Canonical saved-plan resolution

`PlanBuilder.BuildPlan(SavedPlan, …)` is the domain-plan resolver; `Build(SavedPlan, …)` maps that same result into the UI DTO. Its callers already scope reads through `CurrentRunner`/`OwnPlan`, or a worker's runner-owned query. No anonymous input or share-link field can select a private prescription. Ordinary plans still use their pinned generator, race snapshots, accepted calls and revisions.

| Call sites | Resolution and private behavior |
|---|---|
| `MyPlans` Get, CoachMyPlan, SavePlan history capture, replan response | Saved-plan overload. Ordinary same-race edits cannot overwrite a private prescription. Private replan/undo-regeneration is refused with an explanation. |
| `Coaching` weekly review, remaining week, life changes, session adjustments, undo, progress, insights, synced completion | Same resolver; private weekly regeneration and exact pace/distance edits are unavailable. Existing preview/approve/undo reductions use the private schedule and runner-authored evidence. No missed-run catch-up; private moves reject adjacent hard days. |
| `PlanSessions`, additional-run bounds, `RunningLogReader`, `ActivityImporter` | Same private sessions, dates, types, distance and steps for validation, actual-run history and activity matching. A run and gym share a date without sharing identity or completion. |
| `JourneyReader`, race history start date, race result bounds | Same resolver, including archived prescriptions; the prescription is stored intact, not reconstructed from public answers. |
| `ReminderRunner`, `NotificationDeliverer`, `AdditionalNotifications`, weekly recaps and coaching tips | Saved-plan overload at schedule reads. Schedule-bearing push is suppressed for private plans; weekly emails omit the private schedule. No private workouts travel through a third-party notification transport. |
| Personal calendar token feed | Returns 404 for a current private plan. Authenticated private ICS and owner-side calendar/workout file export resolve the private schedule. Subscription links are hidden. |
| Account export/deletion | Export includes prescribed steps, gym movements/completions and all stored imports, never raw preview tokens. Runner deletion cascades to prescriptions/imports. |
| Home, Plan, day, calendar, Strength, pace guide, Progress | Authenticated saved-plan DTO; private Plan never calls the anonymous generator. No share link, generic edit/save or private Home snapshot. Existing actual-run stickers carry actual measurements, not prescribed titles or steps. |

### Precedence and identity

1. Build the pinned generated baseline for race boundaries and week/phase layout. The generator and historical snapshots are unchanged.
2. The private version-1 prescription replaces **all** sessions and pace bands. An omitted day is rest; it never receives a generic substitute. Explicit steps include warm-up/recovery/cool-down in the computed distance. Timed steps use the midpoint of their explicit pace band for estimated distance. Session totals use 0.001 km; the existing weekly total contract rounds to 0.1 km.
3. Apply approved gym date overrides, then existing approved run revisions. Run revisions preserve the immutable original prescription for undo. The private identity in a DTO/ICS follows a moved run's origin; gym IDs stay stable across moves.
4. Weekly generic coaching/replan cannot override private steps. Exact distance/pace editing is explicitly unsupported. Remaining-week easing, travel/illness reductions and safe future run moves use the existing deterministic rules; they never increase a private plan after a single easy session. Logged days and race remain protected. Gym completion is persisted independently of run check-ins; it never enters running mileage/coaching evidence.

The private UI reuses existing disclosures, buttons, tabs, runner waits and both themes. There is no chat, provider integration, adaptive feature enabling or change to the public three-strength-day cap.

Private run adjustments are deliberately not composed with moves: undo upcoming run changes before moving a run, and undo a move before easing/changing that moved run. The existing revision model cannot safely compose those operations without risking a generic or earlier prescription. The API refuses the combination with `private_move_restore_required`; Undo restores the exact private steps. Gym moves/completion stay independent. Eased workouts cap target RPE at the existing easy-effort range, and restoring either end of a run move protects check-ins at both ends.

Private view state is bound to the verified account ID and saved-plan ID. Display names, email addresses and the legacy Home-cache fingerprint are not private ownership keys. Pending gym responses are discarded on account-view cleanup and checked again against that identity before updating App state.

Training-story card sharing is disabled for private current and archived chapters because a tick-only story can contain prescribed distance or schedule totals. Actual recorded-run stickers remain available. The owner can still view the private story and export their account data.
