# Testing safely before a merge

Automated tests must never use Taperday's production database, a database holding real runner data, or a connection copied from production App Service settings. Run tests before merging: every merge to `main` deploys the app and may apply database migrations.

## Use an isolated database

The SQL integration suite applies migrations and **deletes existing rows** with Respawn. Its connection must point to a disposable local SQL Server / LocalDB instance. Use a database name containing `Test`, or the `StartLineCheck…` names generated by `scripts/check.sh`.

`StartLineApiFactory` checks the server and database name before starting the test host. Remote SQL hosts and ordinary application database names are rejected. Do not remove this guard to make a failing test run. GitHub CI supplies its own SQL Server container on `localhost`; it never needs production SQL credentials.

On Windows, the default is `(localdb)\MSSQLLocalDB`, database `StartLine_IntegrationTests`. For Docker on another development machine, use a dedicated container and a generated password:

```bash
test_sql_password="$(openssl rand -hex 24)Aa1!"
docker run -d --name taperday-test-sql \
  -p 127.0.0.1:1433:1433 \
  -e ACCEPT_EULA=Y \
  -e MSSQL_SA_PASSWORD="$test_sql_password" \
  mcr.microsoft.com/mssql/server:2022-latest
export STARTLINE_TEST_SQL="Server=127.0.0.1,1433;Database=Taperday_IntegrationTests;User Id=sa;Password=$test_sql_password;TrustServerCertificate=True"
```

Wait for SQL Server to finish starting before running the checks. The loopback binding keeps this test service local. `TrustServerCertificate=True` is for the disposable local SQL instance, not advice for production. Do not print the connection string, commit it, or put production credentials into this variable.

## Required checks

From the repository root, with the documented .NET SDK and Node installed:

```bash
dotnet tool restore
scripts/check.sh
```

The script checks backend formatting, a strict Release build, all backend tests, EF model/migration consistency, frontend lint, TypeScript, the full frontend suite, production build, dependency audit and Playwright journeys. Keep test worker concurrency low as configured; do not skip tests to get a green result.

For a focused investigation, run the relevant tests first, then the complete checks before merge. A focused pass is not evidence that the full suite passed. Record the tested commit, results, any skipped checks, and device/authentication limitations in the pull request. Do not merge with unexplained failures.

## Verify the whole data journey

For changes to saved running history, asserting that Save sends the right request is insufficient. Verify that the entry remains visible immediately after saving, on its actual calendar date, after navigating away and back, and after a fresh load. Cover rest days, strength days, prescribed-running days, additional runs versus replacements, multiple entries on one date, manual distance/time, time-only logs, uploads, linked Strava activities, and imported cache expiry. Check that the original prescription remains identifiable and that saved totals count each associated run once.

Failures need separate coverage: a failed load must not become empty history; a failed save or delete must retain the form or saved entry; retry and double-clicking must not duplicate it. Late refresh responses must not undo a successful edit or deletion. Account changes must not reveal another plan's entries.

`client/src/features/coaching/RunVisibility.test.tsx` drives actual Home/Plan screens with the real check-in hook and controlled API responses. `useCheckIns.test.tsx` covers refresh races and account/plan boundaries. `client/e2e/run-history.spec.ts` repeats saved-run visibility journeys in a real browser, including keyboard calendar navigation, reduced motion, reload and phone/tablet/desktop/ultrawide widths. These browser fixtures use synthetic authentication and API responses; they do not establish live Entra or production SQL behavior. Their Vite entry under `client/e2e/fixtures/` is test-only and excluded from the production build. The SQL integration suite separately checks API persistence, ownership and imported-run associations against disposable local SQL.

Calendar day changes must also exercise `client/e2e/calendar-day.spec.ts`: selecting rest/workout days, preserving the prescription beside actual runs, explicit source-link deduplication, save/edit/reload, cache removal, time-only entries and failed/successful deletion. `ui-polish.spec.ts` checks the compact day dropdown against the production build and fonts at phone through ultrawide widths. Keep unavailable imported history distinct from an empty day. See [calendar day summaries](calendar-day-summary.md).

## Test sequences across feature boundaries

Changes to plans, logging or persistence require a risk-based sequence matrix, with evidence and remaining gaps recorded in the PR. A collection of isolated save-button tests is insufficient. Exercise log → edit availability/strength/goal/start → failed save/retry → repeated submit → reload → edit the original entry. Combine planned, additional, time-only, tick-only and imported sources. Verify retained IDs/dates, source links, own measurements, honest missing-data states, totals without duplicate counting, and calendar visibility outside a changed plan window. Include stale plan IDs, account ownership, plan replacement/removal and source expiry. See [the lifecycle audit](qa/2026-10-29/plan-history/audit.md).

The focused navigation journey (`client/e2e/focused-training.spec.ts`) verifies the four main destinations, grouped settings and retained profile drafts. When controls move into disclosures, follow those visible controls in tests. Closed native details are not consistently filtered by JSDOM role queries: assert visibility and verify the actual browser path. Calendar regression coverage must include a single tab tap while the inline day is open, including after a viewport/source change.

## Browser and integration boundaries

- Upload/request-limit regressions must include a real loopback Kestrel test (WebApplicationFactory.UseKestrel), not TestServer alone: TestServer does not enforce Kestrel's HTTP body limits. Use realistic payload sizes as well as tiny fixtures. RunnerPhotoHttpTests protects the profile-picture route against the 16 KiB limit mismatch; the browser suite separately exercises real camera-size decoding/compression. See [profile pictures](profile-pictures.md).
- The browser suite runs a local production frontend and local API. Its stateless plan-generation journeys do not need a live database; the E2E API environment skips startup migrations.
- Account, persistence and migration tests use the disposable SQL database and test authentication. Use synthetic runners and recordings.
- Strava tests use the repository's fake provider. Never run sync tests against a real runner's Strava account or call production endpoints to seed/reset test data.
- Emulated mobile screens do not prove physical iPhone, Android or Safari behavior. Report that distinction, particularly for clipboard/image sharing and native share sheets.
- Production deployment health checks and intentionally reviewed migrations belong to the deployment workflow. They are not substitutes for isolated tests, and the test suite must not be pointed at production to validate a deploy.

After testing, remove only your disposable container and clear the local variables:

```bash
docker rm -f taperday-test-sql
unset STARTLINE_TEST_SQL test_sql_password
```
